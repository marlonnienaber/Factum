# Database design

## Categories and tasks migration

This section documents the design decisions represented by
[`20260807212723_create_categories_and_tasks.up.sql`](server/migrations/20260807212723_create_categories_and_tasks.up.sql).

### Task partitions

The application presents a user's tasks through four disjoint partitions. A task belongs to exactly one partition at a time.

| Partition | `trashed_date` | `done` | `date` | `rank` |
| --- | --- | --- | --- | --- |
| Undated and open | `NULL` | `FALSE` | `NULL` | Required |
| Dated and open | `NULL` | `FALSE` | Required | Required |
| Dated and completed | `NULL` | `TRUE` | Required | Required |
| Trashed | Required | Either | Optional; required when done | `NULL` |

Ranks are local to these active partitions. The same rank may therefore be used by different users, by tasks on different dates, or by open and completed tasks. Trashed tasks do not participate in rank ordering.

### `categories`

#### `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`

`id` is the stable identity of a category. `BIGINT` maps naturally to Go's `int64` and leaves ample space for future records. PostgreSQL generates the normal value through the identity sequence, while `BY DEFAULT` still permits an explicit identifier when migrations or controlled data setup require one. The primary key guarantees that the value is non-null and unique.

#### `title VARCHAR(50) NOT NULL`

A category must have a title, and the database enforces the agreed maximum of 50 characters. Category titles are not unique: the identifier, rather than the display title, determines category identity.

Categories do not currently contain a `user_id`. Ownership or per-user category scoping is therefore not part of this migration.

### `tasks`

#### `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`

`id` gives every task a stable identity independently of its rank or current partition. As with category identifiers, it maps to `int64`, is normally generated by PostgreSQL, and may be supplied explicitly for controlled migration or setup work.

#### `user_id BIGINT NOT NULL`

Every task belongs to a user. The value is required because task endpoints always operate on the authenticated user's data; an ownerless task would not be reachable through that model.

#### `category_id BIGINT NOT NULL`

Every task belongs to a category. The relationship is required even though the category-management endpoints are being implemented separately.

#### `title VARCHAR(100) NOT NULL`

A task must have a title. The database mirrors the request validation limit of 100 characters so the invariant also holds for writes that do not pass through the HTTP API.

#### `description VARCHAR(2000)`

The description is optional and is therefore nullable. When present, PostgreSQL enforces the maximum of 2,000 characters. `NULL` represents the absence of a description; it remains distinct from an explicitly supplied empty string.

#### `date DATE`

The date is optional because open tasks can be undated. PostgreSQL's `DATE` type stores only year, month, and day, with no time-of-day or time-zone information. For an open task it places the task in the dated view. A completed task must have a date, enforced by `tasks_done_requires_date_check`.

#### `rank TEXT COLLATE "C"`

Rank is a fractional indexing key generated with `roci.dev/fracdex`, so it is text rather than a numeric position. Fractional keys allow tasks to be inserted or moved without renumbering every surrounding task.

The `"C"` collation makes PostgreSQL compare the keys bytewise. This matches the lexicographic comparisons used by `fracdex`; a locale-dependent database collation could otherwise produce a different order for uppercase and lowercase characters.

Rank is nullable only because trashed tasks do not belong to an ordered active partition. Active tasks must have a rank, while trashed tasks must not have one. This relationship is enforced by `tasks_rank_presence_check`.

#### `done BOOLEAN NOT NULL DEFAULT FALSE`

Every task has an explicit completion state. New tasks are open by default, so callers do not need to provide this implementation-controlled property during creation. A completed task is required to have a date.

#### `trashed_date TIMESTAMPTZ`

`NULL` means the task is active. A value means the task is soft-deleted and records the precise trashing event. Unlike the calendar-only task date, trash ordering requires an instant in time, so `TIMESTAMPTZ` is appropriate. The trash endpoint uses this timestamp together with `id` as its cursor.

When a task is trashed, its rank is cleared. Restoring it requires generating a new rank in its destination partition within the same transactional workflow.

### Foreign keys

#### `tasks_user_id_foreign_key`

```sql
FOREIGN KEY (user_id) REFERENCES users (id)
```

This guarantees that every task owner exists. No `ON DELETE` action is specified, so PostgreSQL prevents deletion of a referenced user until their tasks have been handled explicitly.

#### `tasks_category_id_foreign_key`

```sql
FOREIGN KEY (category_id) REFERENCES categories (id) ON DELETE RESTRICT
```

This guarantees that a task cannot reference a nonexistent category. The create-task endpoint translates a violation of this named constraint into the `category_not_found` response. `ON DELETE RESTRICT` makes the intended category-deletion behavior explicit: a category cannot be deleted while any task still references it. The delete-category endpoint translates that constraint violation into a conflict response rather than deleting the tasks implicitly.

### Check constraints

#### `tasks_rank_presence_check`

```sql
CHECK (
    (trashed_date IS NULL AND rank IS NOT NULL)
    OR (trashed_date IS NOT NULL AND rank IS NULL)
)
```

This encodes both directions of the rank lifecycle:

- An active task must have a rank.
- A trashed task must have no rank.

Encoding both directions prevents ambiguous states such as an unranked active task or a trashed task retaining an obsolete position.

#### `tasks_done_requires_date_check`

```sql
CHECK (done = FALSE OR date IS NOT NULL)
```

An open task may be dated or undated, but a completed task must be associated with a calendar date. Completing an undated task therefore sets its date, normally to the current calendar day. This also prevents completed, undated rows that would belong to none of the supported active views.

### Partition-aware unique index

```sql
CREATE UNIQUE INDEX tasks_untrashed_user_id_done_date_rank_unique
    ON tasks (user_id, date, done, rank) NULLS NOT DISTINCT
    WHERE trashed_date IS NULL;
```

This is a partial unique index because rank uniqueness matters only for active tasks. Trashed rows are excluded by `WHERE trashed_date IS NULL` and consequently do not reserve their former ranks.

Uniqueness applies to the complete `(user_id, date, done, rank)` tuple:

- `user_id` scopes ordering to one user.
- `date` separates undated tasks and each individual calendar date.
- `done` separates the open and completed views.
- `rank` identifies a unique position within that resulting partition.

The order of columns does not change the uniqueness rule: two rows conflict only when all four indexed values are equal.

PostgreSQL normally considers two `NULL` values distinct in a unique index. `NULLS NOT DISTINCT` changes that behavior so two undated tasks for the same user and completion state cannot share a rank. The rank-presence check ensures that `rank` itself is never null for rows included in this index.

The index also supports the active-task access patterns. Queries constrain the user and destination partition before ordering by rank, and task creation can efficiently retrieve the highest rank in that partition before generating the next `fracdex` key.

An application-level existence check is not a replacement for this index: concurrent requests could both observe that a generated rank is absent. Rank lookup, generation, and insertion therefore run together in a serializable transaction, while this index remains the database-level invariant.

### Down migration order

The down migration drops `tasks` before `categories`. This order removes the referencing table before the table targeted by `tasks_category_id_foreign_key`, avoiding a foreign-key dependency error. Dropping `tasks` also removes its check constraints and indexes automatically.
